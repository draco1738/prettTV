# Local settings backup checks

`python tests/settings-backup/run_checks.py` compiles the transfer, guard, backup storage, Activity, readability dependency and three native UI checks against the cached E: toolchain, then runs `SettingsBackupChecks` on the host JVM. The scoped harness reads unchanged validator/style classes from the sibling production checkout; it never writes that checkout, builds an APK or uses a device. Gradle's complete JVM suite compiles all current sources instead.

`SettingsWriterIntegrationTest` adds real writer-API regressions using in-memory SharedPreferences: apps, weather, playback and personalization reject a busy restore without opening editors; old generations and late Undo registration are rejected; all personalization instances invalidate previous Undo; recoveryRequired freezes writers; admitted nested writes finish before restore takes the lock; diagnostic import excludes concurrent writers. Run with Gradle `:app:testReleaseUnitTest --tests fi.jommi.rivi.SettingsWriterIntegrationTest`.

Native registration includes `SettingsBackupAndroidChecks.run(this, ::test)` and `HomeBackupIntegrationAndroidChecks.run(this, ::test)` in the full runner and `settingsBackupOnly=true` selection. The first three checks cover intent non-consent, cancel-first/held-OK confirmation and pause revocation. Two real Home → Backup → Home checks use remote key events to save, change interface size/Watchlist, restore and return; they assert restored dimensions/data, cleared Undo, retained usable focus and rejection of old-generation writes. All five executed successfully on the TCL, both in the 21-check focused follow-up run and the 184-check full run. These totals overlap and are not added together. Failure injection remains host coverage rather than physical disk-failure or power-loss proof.

## Writer integration audit

- `MainActivity`: guarded home editors and whole hide/app arrangement mutations; app-discovery callback epoch; provider delivery/Watchlist consumption epoch; stale dialogs dismissed before backup/import; no departure focus write; sources invalidated before launching the opaque backup Activity. Return waits asynchronously for `!busy`, discards Undo/content/viewport on epoch change, re-reads preferences and restarts sources only outside recoveryRequired.
- `Prefs` (`Apps.kt`): every rivi preference setter, plus whole recency read/modify/write. MainActivity guards multi-field and derived-value app actions with the originating epoch.
- `PlaybackHistory`: exclusion outside historyLock for provider merge and confirmation. `ContentRepository` captures the epoch before queuing provider work and passes it through merge/feedback migration. `PlaybackTracker` drops samples across epoch changes and captures the current epoch before scanning; it does not replay rejected samples.
- `PersonalizationStore`: exclusion outside stateLock for update/import and playback consumption, generation-bound Undo bookkeeping, and automatic history invalidation across instances.
- `WeatherPreferences` / `WeatherRepository`: all three Home preference writes guarded; ZIP request epoch captured before scheduling and checked at publication; old workers cannot publish after restart.
- Diagnostic imports retain their explicit synchronous dump protocol, use nonblocking writer-lock admission plus epoch invalidation, and report actual completion/failure. They are a legacy diagnostic path, not the TV confirmation flow; no claim of background diagnostic disk I/O. Exports refuse busy/inconsistent reads.
- `LocalSettingsTransfer` is the raw validated commit/rollback engine. Production callers are the exclusive local backup restore and guarded diagnostic import. Tests intentionally call it directly on isolated stores.

Only after this integration does MainActivity enable the backup safety gate. Unrelated helper/recovery, updater, Bluetooth output and reminder stores are not among the four backed-up stores and remain outside that gate. No known writer to the four backed-up stores is intentionally left unguarded.

## Diagnostic recovery regression

If an explicit `--restore-local-settings` import fails its rollback and no local snapshot exists, an operator can retry that same diagnostic route with a known-good export. It still validates the complete target plan before editors, requires writer integration and nonblocking exclusive admission, and verifies each store's commit/readback before reporting success. Legacy exports retain their existing personalization-default behavior; this is not permission for a partial restore or an automatic retry. No local recovery snapshot is invented or overwritten.

A failed recovery attempt keeps `RECOVERY_REQUIRED`, including when it successfully rolls back to the already-unverified pre-attempt state or fails before editing. Busy exclusion blocks writers during recovery; the recovery gate blocks them after any failure. Only a completely successful restore clears the gate, and epoch changes reject work queued before/during recovery. MainActivity's existing import validation and recovery-aware source restart remain unchanged. Its recovery dialog now describes a local pre-restore copy as conditional, and identifies explicit diagnostic import of a previously retained known-good export when no valid local copy is available.

Nine focused host regressions in `SettingsBackupChecks` cover recovery without either snapshot, verified/unverified rollback failures, invalid input before editors, last-store readback mismatch, failure before editing, concurrent imports/writers, the unintegrated gate, and ordinary verified rollback. They use the real transfer/guard code with synthetic in-memory preferences that change memory before failed commits.

Executed scoped evidence for this defect: baseline `OK (23 tests)`; fail-first additions `Tests run: 31, Failures: 8` against the original guard; isolated negative control removing only sticky recovery state `Tests run: 32, Failures: 3`; final fixed source `OK (32 tests)`. Run `python tests/settings-backup/run_checks.py` to repeat the host suite. The negative control modifies only an evidence-directory source copy, not the working tree. This is host evidence, not execution of MainActivity or Android filesystem/device recovery.

## Limits

Snapshot file publication is checksummed, staged, synced, verified and atomically replaced. Restoring four preference stores is **not** a single crash-atomic filesystem transaction. Rollback and restoreState are process-local guarantees; power loss/process death can require manually reviewing the pre-restore copy. Cancellation revokes subsequent writes and drains rollback; an already-started OS commit can finish. Local snapshots do not survive uninstall/clear-data, do not include accounts or Android settings, and are not off-device backups.
